# Stumping Qwen3.5-9B on OpenResearcher questions, targeted distillation, and retraining the retriever without the test set

Date: 2026-09-09
Companion to: `docs/roadmap_to_90_percent_bcp.md` (the phased roadmap). This document replaces that roadmap's Phase 2 (question factory) with the OpenResearcher question pool, and adds the retriever-retraining track that the roadmap did not cover because the retriever contamination was not known then.

---

## 0. Summary

1. **What you have found is worse than the model contamination.** The dense encoder adapter (`DanielTobi0/qwen3-embedding-8b-browsecomp-lora-v2`), the FAISS index built from it, and the reranker adapter (`DanielTobi0/qwen3-reranker-0.6b-browsecomp-lora-v3`) were trained on the BrowseComp-Plus queries and their evidence documents. That means every retrieval number in the audit (58% evidence recall) and the 57% end-to-end score are measured with a retriever that has memorised the answers to the test questions. The first thing to do is re-measure the agent with a clean, public retriever so you know your real starting point. Expect a large drop.

2. **OpenResearcher is a good replacement question pool, with two catches.** It is a TIGER-AI-Lab release (paper arXiv 2603.20278): about 96,000 long-horizon research trajectories generated by gpt-oss-120b with `search`, `open`, and `find` tools over a self-built corpus of roughly 15 million documents (about 11 billion tokens), with the corpus, dataset, model, and evaluation logs released on Hugging Face. The catches: (a) the questions are answerable from *their* corpus, not from the 100k BrowseComp-Plus corpus, so stumping and distillation must run in *their* search environment, not yours; (b) the trajectory tool interface (`search`/`open`/`find`) is not your `search`/`get_document` interface, so you must pick one interface and use it everywhere.

3. **Stumping is the right idea and it is cheap relative to what follows.** Run the student several times per question in the OpenResearcher environment, record pass rates, classify failures, and send only the informative failures (not the impossible ones, not the trivial ones) to the teacher. Part 2 is the full procedure; Part 3 is the issue list.

4. **Yes, you can retrain the retriever on OpenResearcher data, and you should.** The teacher trajectories contain the ideal supervision: the queries an agent actually issues and the documents it actually opened and used. Mine (query, positive document, hard negatives) triples from them, train the encoder and reranker on those, re-encode the BrowseComp-Plus corpus, and rebuild the index. Part 4 is the step-by-step guide. BrowseComp-Plus qrels are then used only to *report* retrieval quality, never to train or select.

5. **Where the retriever is explained.** `bcp-replication/REPLICATE.md` is the full explanation (pipeline, artifacts, traps, configuration, verification). `bcp-replication/retrieval_api.md` is the client-facing API contract with measured latency. `bcp-replication/AGENT.md` is the ordered rebuild runbook. The code itself is `bcp-replication/searcher/searchers/hybrid_searcher.py`, whose docstring diagrams the pipeline. See Part 5.

6. **One security item.** `bcp-replication/Retrieval_API.txt` has a retrieval bearer token, public IP, and SSH port committed to git. The instance is probably gone, but the file should be scrubbed and the token treated as burned.

## 1. What OpenResearcher is, and what it means for you

### 1.1 The facts I could verify

From the project README and search results (Hugging Face and arXiv are blocked from this session, so the dataset card and paper could not be read directly; verify the items marked "check" when you open them):

| Item | What is known |
|---|---|
| Origin | TIGER-AI-Lab (University of Waterloo group), "OpenResearcher: A Fully Open Pipeline for Long-Horizon Deep Research Trajectory Synthesis", arXiv 2603.20278 |
| Trajectories | About 96,000 (the paper says over 97,000 synthesized), generated by gpt-oss-120b with native browser tools; a long tail has 100-plus tool calls |
| Tools | Three browser primitives: `search` (query to result list), `open` (fetch a page or result), `find` (locate a string inside the open page) |
| Corpus | Self-built, roughly 15 million documents, about 11 billion tokens, released as `OpenResearcher/OpenResearcher-Corpus`; the search loop runs fully offline over it |
| Search backends | BM25 and Qwen3-Embedding-8B dense search; corpus embeddings are provided for local dense deployment |
| Dataset fields | Rows are `messages` lists containing reasoning, tool calls, observations, and final responses (check: whether a separate gold-answer field exists, and where the questions came from) |
| Released artifacts | `OpenResearcher/OpenResearcher-30B-A3B`, `OpenResearcher/OpenResearcher-Dataset`, `OpenResearcher/OpenResearcher-Corpus`, `OpenResearcher/OpenResearcher-Eval-Logs`; code at `github.com/TIGER-AI-Lab/OpenResearcher` (`browser.py`, `backend.py`, `deploy_agent.py`, `eval.py`, `scripts/start_search_service.sh`) |
| Result | The 30B-A3B model trained on this data scores 54.8% on BrowseComp-Plus, using a plain BM25 or Qwen3-Embedding-8B retriever with no fine-tuning |
| Training | SFT with Megatron-LM (check hyperparameters); no RL reported in the README |

### 1.2 What it means

- **The questions are not answerable from your corpus.** The BrowseComp-Plus corpus is 100,195 documents chosen specifically around the 830 benchmark questions. OpenResearcher questions were solved against a 15-million-document corpus. If you stump the student against your retrieval service, most failures will be "the evidence does not exist here", which teaches you nothing. Stumping, teacher generation, and any RL on these questions must use the OpenResearcher corpus and search environment. Your BrowseComp-Plus retriever stays for evaluation.

- **The 54.8% number calibrates expectations.** A 30B model with 3B active parameters, trained on all 96k trajectories, scores 54.8% on BrowseComp-Plus with an untuned retriever. A 9B trained on a subset of the same questions will not beat that by distillation alone. The value of stumping is to spend your teacher budget where the student is weak; the value of the harness work in the roadmap (evidence notes, fresh-context answerer, ensembles) stacks on top. The 90% target still needs everything in the roadmap.

- **The `find` tool matters.** `find` lets the model locate a string inside a long opened page instead of reading it whole. That is a direct fix for "the answer was in the document and the model missed it". I recommend adding `find` to your harness for BrowseComp-Plus as well (the benchmark README explicitly allows browsing tools) so that the student sees one interface in training and evaluation.

- **You get free teacher data.** Around 96k gpt-oss-120b trajectories already exist. Those on questions the student fails are usable as distillation data today, after format conversion, without paying for a single teacher call. GLM (or any other teacher) is then reserved for questions gpt-oss-120b also failed, or for regenerating trajectories in your exact interface.

### 1.3 Decisions to make before starting

| Decision | Recommendation | Why |
|---|---|---|
| Which environment for stumping and distillation | The OpenResearcher offline environment (their corpus and search service), deployed by you | Questions are only answerable there |
| Tool interface | One three-tool interface everywhere: `search`, `get_document` (their `open`), `find`; keep your names, map theirs | Student must see one interface; `find` helps evidence use |
| Which student to stump | Current Atom Electron 1.3 adapter | It formats tool calls reliably and has never seen these questions; the contamination on BrowseComp-Plus does not affect OpenResearcher questions. Re-stump after each new SFT round. |
| Number of attempts K | 4 for the first pass, 8 for the final learnable-zone labelling | Cost; Part 2.5 |
| Teacher | Existing gpt-oss-120b trajectories first; GLM (your named choice) for the remainder and for regeneration in your interface | Free data first; teacher exposes reasoning either way |
| Retriever for BrowseComp-Plus reporting | Public Qwen3-Embedding-8B index plus a reranker that has never seen BrowseComp-Plus, until the retrained one exists | Honest baseline |

## 2. The stumping plan, step by step

"Stumping" here means: run the student on every candidate question several times in the training environment, record whether it succeeds, and use the pass rate to decide what the teacher should demonstrate. It is hard-example mining. The output is a labelled question pool with, for each question, a pass rate, a failure class, and a decision (distil, keep as retention example, or discard).

### Step 1. Inventory the dataset (one day)

1. Download `OpenResearcher/OpenResearcher-Dataset` and `OpenResearcher/OpenResearcher-Eval-Logs`. Read the dataset card and the paper before anything else.
2. Extract the unique questions. 96k trajectories may map to fewer unique questions (several attempts per question) or to 96k distinct ones; the count decides everything downstream.
3. For each question, determine the **gold answer**. Three possibilities, in order of preference:
   - a gold-answer field exists in the row: use it;
   - no field, but the trajectories have final answers and multiple trajectories exist per question: take the answer if a majority agrees, otherwise mark "unverified";
   - neither: run a strong model with the trajectory's opened documents (oracle mode) to produce and verify an answer; mark "derived".
   Record the provenance (`gold_source: field | consensus | derived`). Only `field` and `consensus` questions are used for stumping in the first pass.
4. Record per question: the number of teacher trajectories, whether any is marked correct, the tool-call count and token length of the shortest correct trajectory, the documents opened, and the final answer. You will need the opened documents for the retriever (Part 4).
5. Check the licence of the dataset and of the corpus, and the terms of the teacher you plan to use for regeneration.

### Step 2. Decontaminate against BrowseComp-Plus (one day)

Do this before any compute is spent, and re-run it whenever the pool changes.

1. Exact and normalised match of every OpenResearcher question against the 830 benchmark questions.
2. Embedding similarity (Qwen3-Embedding, cosine) of every OpenResearcher question against every benchmark question; drop anything above 0.85 and put 0.75 to 0.85 in a file for a human to skim.
3. Normalised match of every gold answer against every benchmark gold answer; drop matches unless the answer is a very common string (a year, a country), in which case check the question by hand.
4. Document overlap: if the OpenResearcher corpus contains pages that are also BrowseComp-Plus evidence or gold documents (both are web crawls; overlap is likely), that is acceptable for *questions* but must be tracked for the *retriever* (Part 4.3). Build the overlap table now: hash normalised text and titles of the 100,195 BrowseComp-Plus documents and look them up in the OpenResearcher corpus.
5. Write the excluded IDs and the reason to a manifest committed to the repo.

### Step 3. Stand up the training environment (three to five days)

You need a search service over the OpenResearcher corpus that your harness can call.

1. Follow the OpenResearcher repository (`setup.sh`, `scripts/start_search_service.sh`, `browser.py`, `backend.py`) to deploy their offline search over their corpus and embeddings. Their dense backend uses Qwen3-Embedding-8B; the provided corpus embeddings save you from encoding 11 billion tokens yourself (that would be roughly 100 to 200 H100-hours).
2. Wrap it behind the same HTTP contract your harness already speaks (`POST /retrieve`, `GET /get_document`), plus a new `find` endpoint (`docid`, `pattern`, returns matching passages with offsets). The simplest path is a thin adapter service in front of their backend; the harness then switches environments with one URL.
3. Add `find` to `chat_client.py` as a third tool, behind a flag, and add it to the BrowseComp-Plus retrieval service too (it is a string search over `get_document` text; no GPU).
4. Throughput: the OpenResearcher corpus is 150 times larger than yours, so dense search over it is heavier. Measure searches per second at concurrency 4, 8, and 16. You need at least 3 to 5 per second for stumping (Step 5 arithmetic). If you cannot get there, use BM25-only for stumping and note the mismatch, or add replicas.
5. Freeze the environment: snapshot the exact index files, model versions, `k`, snippet length, and tool descriptions in a manifest. Every stumping result records the manifest hash.

### Step 4. Choose the stumping sample (half a day)

Do not stump all 96k at once. Stratify by the fields from Step 1 (teacher tool-call count, answer type, whether the teacher succeeded, question length) and draw 10,000 to 20,000 questions for the first pass. Reserve 500 as an OpenResearcher dev set and 500 as an OpenResearcher test set; freeze them; never train on them.

### Step 5. Run the student (one to two weeks of wall time, mostly waiting)

1. Model: the current adapter on vLLM, the harness with the three tools, evidence notes if you have already built them (Roadmap Part 4.1; if not, raw snippets, but then re-stump later because the format changes behaviour), temperature 0.7, tool ceiling 32, per-turn `max_tokens` 8,192, context 32k with compaction.
2. K = 4 attempts per question with different seeds. Write one JSON per attempt in the existing `run_qid_*.json` schema plus the attempt index, so all your analysis tooling works.
3. Arithmetic for 20,000 questions × 4 attempts × about 15 searches = 1.2 million searches. At 5 searches per second that is 67 hours of retrieval time. Model side: 80,000 episodes × about 10,000 generated tokens = 800 million tokens; two H100s under vLLM at a few thousand tokens per second each is one to two days. Retrieval, not the model, is the bottleneck; plan replicas accordingly.
4. Resumability: per-attempt files, skip existing, a supervisor that restarts on crash, and a nightly count. Your `AGENTS.md` history shows what happens without this.

### Step 6. Judge and diagnose (automatic, runs alongside Step 5)

1. Correctness: normalised match against the gold answer and aliases; LLM judge only on non-matches; cache judgments by (question, normalised answer). Use the same frozen judge prompt as the benchmark evaluator so the notion of "correct" is consistent.
2. Per-attempt diagnostics, all already produced by the harness or cheap to add: tool calls by type, rejected duplicates, refusal, budget exhaustion, truncation, documents opened, whether the gold string appeared in any tool output (surfacing), whether any teacher-opened document was retrieved (teacher-document recall, the OpenResearcher analogue of evidence recall), stated confidence.
3. Per-question aggregates: pass rate over K, mean surfacing rate, mean teacher-document recall, dominant failure class.

### Step 7. Classify every failed question (automatic, with a 200-question manual audit)

Assign one class per question using the aggregates; this determines what to do with it:

| Class | Rule | Action |
|---|---|---|
| Impossible in environment | Teacher also failed on every trajectory, or gold answer unverified | Discard from distillation; keep in a separate file |
| Surfacing failure | 0/K correct, gold string never surfaced, teacher-document recall low | Distil (teaches query strategy); also a retriever training signal |
| Conversion failure | 0/K or low pass rate, gold surfaced in most attempts | Distil (teaches evidence use); highest priority, this is your named problem |
| Refusal | Explicit no-answer in most attempts with budget left | Distil; also DPO pairs |
| Loop or budget | Duplicates or ceiling hit in most attempts | Distil; also DPO pairs |
| Format or truncation | Invalid final or length-limited | Fix harness settings before counting as a model failure |
| Judge disagreement | Attempts produce the gold answer under normalisation but the judge says no | Fix normaliser; not a model failure |
| Learnable | 1 to K-1 correct | Keep for RL (learnable zone); include one correct student attempt in RFT data |
| Solved | K/K correct | Do not distil; keep 10 to 20% as retention examples in SFT |

Read 200 questions by hand across classes. The automatic rules will be wrong on some, and the manual sample tells you how wrong.

### Step 8. Build the distillation target list

Priority order for teacher budget: conversion failures, refusals, loops, surfacing failures, then learnable questions with pass rate 1/K. Cap per answer type and per topic so the set is not dominated by one kind of question. Target 5,000 to 10,000 questions for round one.

### Step 9. Obtain teacher trajectories

1. **Reuse first.** For every target question that has a correct gpt-oss-120b trajectory in the dataset, convert it into your tool interface (`search` stays, `open` becomes `get_document`, `find` stays) and your message format (thinking inside the assistant turn, tool results as tool messages). Filter with the same rules as the roadmap Part 6.3: correct final, at least one document opened, no duplicate loops, complete answer contract. Prefer the shortest correct trajectory.
2. **Generate with GLM for the rest**, through your own harness in the OpenResearcher environment, two to four attempts at temperature 0.6 to 0.8, same filters. Also regenerate with GLM on a 20% sample of the reused questions so the student sees the teacher style you will use going forward; compare student results trained on each source before committing to one.
3. **Length discipline.** OpenResearcher's long tail has 100-plus tool calls; those trajectories will not fit a 32k-token student context. Either drop trajectories above your ceiling, or convert them with compaction (replace old tool results with evidence notes, exactly as the harness will do at inference) so that the student trains on the same compacted form it will see.
4. **Closed-book check.** For each target question, ask the teacher without tools. If it answers correctly, the teacher may be recalling rather than researching; keep the trajectory only if it still shows genuine searching, and flag the question.

### Step 10. Train, evaluate, re-stump

1. SFT as in the roadmap Part 6.4 and 6.5 (one row per trajectory, loss on assistant turns only, identity rows mixed in at 5 to 10%, retention examples from the solved class).
2. Evaluate on: the OpenResearcher dev set (single attempt), the frozen BrowseComp-Plus failure-100 and pass-100 sets, the strict split with the *clean* retriever, and the identity controls.
3. Re-stump the new student on a fresh 10k sample plus the round-one failures. Questions that flipped from failed to solved show what was learned; questions that stayed failed are round-two targets. Two to three rounds is typical before returns diminish.

### Step 11. Hand the labelled pool to RL

After round two or three, the pass-rate labels on the learnable class are exactly the input the roadmap's Part 7.8 needs. The environment from Step 3 is the RL environment.

## 3. Everything that can go wrong, and what to do about it

Grouped by where it bites.

### 3.1 Data problems

| Issue | Symptom | Mitigation |
|---|---|---|
| No gold answers, or teacher answers are wrong | Pass rates meaningless; you distil wrong answers | Step 1's provenance rule; use only `field` and `consensus` questions at first; audit 100 by hand |
| Questions are easy or closed-book answerable | Student "passes" without searching; teacher recalls from memory | Closed-book check on both student and teacher; discard questions the base model answers without tools |
| Duplicate or near-duplicate questions | Inflated counts; dev/test leakage | Dedupe by normalised text and by embedding before splitting |
| Questions derived from BrowseComp or from public BrowseComp-style sets that overlap the benchmark | Contamination re-enters through the side door | Step 2 in full, including the answer match and the human skim of near misses |
| Question distribution differs from BrowseComp-Plus (fewer constraints, different answer types, longer horizons) | Gains on OpenResearcher dev do not transfer | Stratify the stumping sample toward BrowseComp-like items (multi-constraint, short unique answers); keep the failure-100 as the transfer check; supplement with the roadmap's synthetic factory later |
| Licence or terms restrictions | Cannot publish a model trained on the data | Read the dataset and corpus licences and the teacher's terms before training |

### 3.2 Environment problems

| Issue | Symptom | Mitigation |
|---|---|---|
| Stumping against the wrong corpus | Everything fails; failures are all "surfacing" | Never stump OpenResearcher questions against the BrowseComp-Plus service |
| Tool interface mismatch between teacher data, training, and evaluation | Student calls tools that do not exist or ignores `find` | One interface everywhere; convert reused trajectories; unit-test the converter |
| Retrieval too slow | Stumping takes months | Step 3.4 throughput target; replicas; BM25-only fallback; query cache keyed on normalised text (attempts on the same question repeat queries) |
| Environment drift mid-run | Pass rates not comparable across days | Manifest hash on every record; do not change the index, `k`, snippet length, or tool descriptions during a pass |
| Service crashes, network faults, Vast rebuilds | Half-finished runs, quarantines | Per-attempt files, resume-by-skip, supervisor restart, and classify records by `status` before counting (your existing practice) |
| Long OpenResearcher pages | Tool outputs blow the context | `get_document` truncation plus `find`; evidence notes |

### 3.3 Student and harness problems

| Issue | Symptom | Mitigation |
|---|---|---|
| Stumping with an unrepresentative harness | Failures are harness artefacts (truncation, no `get_document`) | Fix format/truncation classes first (Step 7), then count; stump with the harness you will evaluate with |
| Temperature and seed noise | Pass rate 1/4 vs 2/4 is noise | Treat classes as bands, not point estimates; K=8 before RL labelling |
| Student changes after SFT | Old failure list stale | Re-stump every round (Step 10.3) |
| Identity adapter interference | Odd refusals or persona text in research | Include identity controls in every evaluation; keep identity rows in SFT |

### 3.4 Teacher problems

| Issue | Symptom | Mitigation |
|---|---|---|
| Teacher fails the hardest questions | Distillation set biased toward medium difficulty | Accept; those go to RL later; log the teacher pass rate per class |
| Teacher format differs (thinking tags, tool-call JSON, citation style) | Student learns a mixed style | Convert everything into the Qwen3.5 chat-template form; validate with the tokenizer preflight your trainer already has |
| Teacher trajectories far longer than the student's context | Truncated training rows or silent drop | Compaction-in-conversion (Step 9.3); hard length cap with a count of what was dropped |
| Teacher hallucinated a correct answer without evidence | Student learns to guess | Require the answer string to appear in an opened document or note; require a supporting citation |
| Two teachers with different habits (gpt-oss-120b reuse vs GLM) | Style conflict | Train two small variants and compare; or use one teacher for all round-one data |
| Teacher refuses or moralises on some questions | Missing coverage on a topic | Log and route to the other teacher |

### 3.5 Training and evaluation problems

| Issue | Symptom | Mitigation |
|---|---|---|
| Training only on failures | Student over-searches on easy questions; loses stopping judgement | 10 to 20% solved retention examples; length-balanced sampling |
| Judge inconsistency between stumping and benchmark | Different notions of correct | Same frozen judge prompt and normaliser everywhere |
| Wins on OpenResearcher dev, no change on BrowseComp-Plus failure-100 | Distribution mismatch | Roadmap Part 4 harness changes; add BrowseComp-like synthetic questions; check retriever transfer |
| Forgetting general ability | Control tasks degrade | Identity/control mix; evaluate controls every checkpoint |
| Cost overrun | Teacher API spend | Reuse existing trajectories first; cap GLM attempts at two per question; stop early on questions already covered |

## 4. The retriever: what it is, what the contamination means, and how to retrain it on OpenResearcher data

### 4.1 What the retriever currently is

From `bcp-replication/REPLICATE.md`, `bcp-replication/retrieval_api.md`, and the docstring of `bcp-replication/searcher/searchers/hybrid_searcher.py`:

```
query --+--> BM25 (Lucene, Tevatron/browsecomp-plus-indexes)         --> top 100 --+
        |                                                                          +--> RRF fusion (k=60) --> reranker cascade --> top 10
        +--> dense (FAISS, Qwen3-Embedding-8B + LoRA v2, 20 shards)  --> top 100 --+
```

| Component | Base | Fine-tuned part | Where it lives |
|---|---|---|---|
| Bi-encoder (dense) | `Qwen/Qwen3-Embedding-8B` | LoRA `DanielTobi0/qwen3-embedding-8b-browsecomp-lora-v2` (private) | merged at load; `--embedding-lora` |
| Dense index | encoded by the fine-tuned encoder | `DanielTobi0/browsecomp-plus-qwen3-embedding-8b-finetuned-index-v2` | `indexes/qwen3-embedding-8b-finetuned-v2/corpus.shard*.pkl` |
| Cross-encoder (reranker) | `Qwen/Qwen3-Reranker-0.6B` | LoRA `DanielTobi0/qwen3-reranker-0.6b-browsecomp-lora-v3` (private); "training positives included evidence documents" | `--reranker-lora` |
| Rerank cascade | all fused candidates (up to 200) scored at 512 tokens, top 20 rescored at 8,192 tokens | | `--rerank-stage1-length`, `--rerank-stage1-keep` |
| Rerank token cache | pre-tokenised corpus for the reranker | built by `scripts_build_index/build_rerank_token_cache.py` | `indexes/rerank-token-cache` |
| BM25 | Lucene index from upstream | none | `--bm25-index-path` |

The two fine-tuned adapters and the index are a matched pair: the index was encoded by the LoRA-v2 encoder, and queries must be encoded by the same adapter with the same pooling (the EOS trap in REPLICATE.md section 5.1).

### 4.2 What "trained on the test data" means here

Both adapters were trained with BrowseComp-Plus queries as the queries and the labelled evidence or gold documents as positives. Consequences:

- The dense encoder has seen each benchmark question paired with its evidence documents. When the agent issues the full question or a close paraphrase, the encoder retrieves the memorised documents. Reported evidence recall (58% mean in the audit) is not a measurement of retrieval skill.
- The reranker has seen (benchmark question, evidence document) pairs labelled positive. It will promote those documents for those queries.
- The end-to-end 57% (and the 52.8% audited run) is therefore measured with a retriever that partially knows the answers. It cannot be compared to the paper's table, where GPT-5 scores 70.1% with an *untrained* Qwen3-Embedding-8B.
- The model contamination (126 questions) and the retriever contamination compound: on those 126 questions both components had seen the answer.

**First action: establish the honest baseline.** Rebuild the service with the public, unfine-tuned components and rerun the strict split with the current adapter:

- dense: `Qwen/Qwen3-Embedding-8B` with the upstream index from `Tevatron/browsecomp-plus-indexes` (the README's `download_indexes.sh` fetches it), no LoRA;
- reranker: `Qwen/Qwen3-Reranker-0.6B` or `-8B` with no LoRA (the cascade code works unchanged; the token cache must be rebuilt if the tokenizer or prefix differs);
- everything else identical.

Report this number as the starting point. It is the only number you can defend today.

### 4.3 Can you train the retriever on OpenResearcher data instead? Yes

What a retriever needs to learn from is (query, relevant document, non-relevant documents) triples. OpenResearcher trajectories contain, for every solved question, the queries a research agent actually issued and the documents it opened and used. That is closer to the agent's real query distribution than the full benchmark question, which is what the contaminated adapters were trained on. Two cautions:

1. The positives must be documents from the OpenResearcher corpus (they are; the trajectories opened them there). The retriever is then applied to the BrowseComp-Plus corpus at evaluation time. Both corpora are web pages, so the transfer is reasonable, but measure it (Step R7).
2. Some OpenResearcher corpus pages are probably also BrowseComp-Plus evidence pages. Training the encoder on (OpenResearcher query, that page) is not benchmark contamination because the query is different, but it does mean the encoder has embedded that page during training. For a clean claim, exclude from training any positive whose text hash appears in the BrowseComp-Plus evidence or gold qrel documents (about 5,000 documents; the overlap table from Part 2 Step 2.4 gives you this).

### 4.4 Step-by-step retriever retraining

**R1. Mine triples from trajectories (two to three days of scripting).**

For each question with at least one correct trajectory (teacher's final answer matches gold):

1. Walk the trajectory. For every `search` call, record the query string and the result list (docids or URLs). For every `open`, record the document. For every `find`, record the document and the pattern.
2. Positives for the question: documents that were opened *and* either contain the final answer string, or were the target of a `find` that returned a hit, or are cited in the final response. Cap at 5 per question.
3. Query set for each positive: (a) the search query whose result list contained that document immediately before it was opened; (b) the full question; (c) optionally the student's own successful queries from stumping. This gives two to four (query, positive) pairs per positive.
4. Hard negatives for each pair: other documents in the same search result list that were *not* opened and do *not* contain the answer string; plus 5 to 10 documents retrieved by the current public dense encoder for that query, excluding positives and answer-bearing documents. Store 10 to 20 negatives per pair.
5. Resolve every docid to full text from `OpenResearcher/OpenResearcher-Corpus`. Drop pairs whose documents are missing.
6. Deduplicate pairs; cap pairs per question at 8 so long trajectories do not dominate.
7. Expect 100k to 500k pairs from the full dataset. Tens of thousands are enough for a LoRA.

Write the output in Tevatron's training JSONL format (`query`, `positive_passages`, `negative_passages` with `docid`, `title`, `text`), which the repository's `scripts_build_index/qwen3-embed.md` already assumes for encoding.

**R2. Split and decontaminate.**

Hold out 2,000 questions (all their pairs) as the retriever dev set. Remove pairs whose positive text hash matches a BrowseComp-Plus qrel document (Part 4.3). Remove pairs from any question excluded in Part 2 Step 2.

**R3. Train the bi-encoder (one GPU, hours).**

Use Tevatron (the tool the upstream repository documents) with LoRA on `Qwen/Qwen3-Embedding-8B`:

| Setting | Value | Why |
|---|---|---|
| Loss | InfoNCE contrastive with in-batch negatives plus the mined hard negatives | Standard dense-retrieval training |
| Pooling and normalisation | EOS pooling, L2-normalise, fp16 or bf16 | Must match what the hybrid searcher does at query time (REPLICATE.md section 5.1; do not append an extra EOS) |
| Query prefix | `Instruct: Given a web search query, retrieve relevant passages that answer the query\nQuery:` | The prefix the searcher already uses |
| Passage prefix | empty | Matches the upstream index recipe |
| Query max length | 512 (raise to 1,024 if full questions are long) | |
| Passage max length | 2,048 to 4,096 | Upstream used 4,096 |
| LoRA | rank 32, alpha 64, all linear layers | Same regime as the existing adapters |
| Learning rate | 1e-4, cosine, 5% warmup | |
| Batch | as large as memory allows with gradient caching (Tevatron's GradCache) | Contrastive training benefits from large batches |
| Temperature | 0.02 | Qwen3-Embedding recipe |
| Epochs | 1 to 2 | |
| Hard negatives per query | 7 | |

Evaluate every few hundred steps on the retriever dev set: Recall@10 and Recall@100 of the positives among the OpenResearcher corpus subsample (build a small FAISS index over the dev positives plus 200k random corpus documents for a cheap proxy).

**R4. Re-encode the BrowseComp-Plus corpus and rebuild the dense index (one GPU, one to two hours).**

1. Encode all 100,195 documents with the new encoder using the exact command shape in `scripts_build_index/qwen3-embed.md` (passage max length 4,096, EOS pooling, normalise, empty passage prefix).
2. Save shards in the format `hybrid_searcher._load_dense_index` reads: pickled `(reps, docids)` tuples, `reps` as float32 arrays, one file per shard matching `corpus.shard*.pkl`.
3. Point `--index-path` at the new shards and `--embedding-lora` at the new adapter. These two must change together (matched pair).

**R5. Train the reranker (one GPU, hours).**

`Qwen/Qwen3-Reranker-0.6B` (or `-4B`/`-8B` if latency allows) with LoRA, pointwise yes/no training on the same triples:

1. Input format must be exactly the scaffolding in `hybrid_searcher.py` (`RERANK_PREFIX`, `RERANK_TASK`, `<Instruct>/<Query>/<Document>` head, `RERANK_SUFFIX`), because inference builds the prompt that way.
2. Label: `yes` for positives, `no` for negatives; loss is cross-entropy on the `yes`/`no` logits at the final position (the Qwen3 reranker recipe).
3. Negatives: the hard negatives from R1 plus top-50 candidates from the *new* dense encoder for each query, excluding positives and answer-bearing documents. This is where reranker gains come from: it must learn to demote what the encoder wrongly promotes.
4. Document truncation at 512 tokens for 70% of examples and 8,192 for 30%, so the cascade's stage-1 and stage-2 both see in-distribution lengths.
5. After training, rebuild the rerank token cache (`scripts_build_index/build_rerank_token_cache.py`) as REPLICATE.md section 5.7 instructs; a stale cache is silently refused.

**R6. Deploy and gate.**

Update `bcp-replication/service/bcp-retrieval.sh` with the new adapter IDs and index path, restart, and run every gate in `bcp-replication/AGENT.md` section 4 (corpus integrity, token cache loaded, adapters loaded, deterministic ranking, latency, auth).

**R7. Measure honestly.**

Run `bcp-replication/scripts_evaluation/eval_retrieval.py` and the upstream `trec_eval` recipe from the README against `qrel_evidence.txt` and `qrel_golds.txt` for three configurations: the public baseline (4.2), the contaminated pair (for the record only), and the new OpenResearcher-trained pair. Report Recall@5/100/1000 and nDCG@10. The qrels are used here only to *evaluate*; selection between checkpoints is done on the OpenResearcher retriever dev set (R3), never on these numbers, otherwise you re-introduce test-set selection.

Then rerun the agent on the strict split with the new retriever and compare surfacing rate and evidence recall against the public baseline.

**Expected outcome.** Below the contaminated numbers, above the public baseline. The paper's Qwen3-Embedding-8B gets evidence Recall@100 of 47.7% on the full question; a retriever trained on agent-issued queries should mainly improve Recall@10 for the short, constraint-style queries the agent actually sends, which is what raises the surfacing rate.

### 4.5 Retriever-specific issues and mitigations

| Issue | Symptom | Mitigation |
|---|---|---|
| False negatives among hard negatives | Training pushes away relevant pages; recall drops | Exclude any negative containing the answer string; exclude documents the teacher opened; cap negatives from the same page domain |
| Encoder and index out of sync | Dense recall collapses toward zero, BM25 normal | Always rebuild the index after changing the encoder; keep `eval_retrieval.py` in the deploy gate |
| EOS pooling mismatch | Recall@100 silently drops from ~0.76 to ~0.65 | Use the tokenizer's default termination; never append `eos_token` (REPLICATE.md 5.1) |
| Query-length mismatch | Good on short queries, poor on full-question queries or vice versa | Include both query types in training (R1.3) |
| Corpus domain shift | Strong on OpenResearcher dev, weak on BrowseComp-Plus | Measure both (R7); if the gap is large, add the roadmap's synthetic BrowseComp-Plus-corpus questions as a second training source, generated from non-qrel documents |
| Reranker prompt drift | Reranker scores random | Train with the exact scaffolding strings from `hybrid_searcher.py`; add a unit test that renders one example from both paths and compares |
| Memory during 8B encoder training | OOM | LoRA plus gradient caching; batch 16 to 32 per device with GradCache chunks; bf16 |
| Token cache stale | 2 s slower per query, silent | Rebuild after any reranker change; check the log line in REPLICATE.md 5.7 |
| Private-adapter dependency | Rebuild fails without the old token | Publish the new adapters to your own organisation's repos and update `download_all.py` |
| Selecting checkpoints on BrowseComp-Plus qrels | Test-set selection | Select on the OpenResearcher retriever dev set only |

### 4.6 Alternative if you want retrieval fixed sooner

Skip training entirely for now: public `Qwen3-Embedding-8B` index plus public `Qwen3-Reranker-8B` (no LoRA), with the deep-pool scan and multi-query search from the roadmap Part 4.4. This is honest, needs no data work, and lets the agent-side work proceed while the retriever data pipeline is built.
